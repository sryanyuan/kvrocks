# 从 L6 小文件积累到写入降速：Kvrocks 碎片问题排查

一个 Kvrocks 实例持续运行后，RocksDB 的 L6 文件数量从 292 个增加到 1155 个，总大小却一直在 30 GiB 左右。其中超过六成文件不足 1 MiB，最小的只有 3185 B，里面只有一条记录。

这些小文件是过期清理留下的残余，还是某些 slot 的写入特别集中？继续追踪后发现，一项用于减少 compaction IO 的提前切分优化，在特定 key 分布和历史文件布局下，反复切出了很小的 SST。它们随后通过 trivial move 进入 L6，又因为很少被重写而长期保留。

另一组同为 RocksDB 9.3.1 的实例日志，展示了碎片积累到更大规模后的后果：L6 超过 50 万个文件，单文件 trivial move 的提交阶段中位耗时从约 0.25 秒升至约 5 秒，上层随后出现容量积压，最终触发写入降速和停写。

本文先用第一组实例数据解释小文件如何形成，再用第二组日志分析文件数量、版本更新成本与写入反压之间的联系，最后讨论为什么在“递增 key + 相同 TTL”的业务中，periodic compaction 可以用来规避这类小文件的长期积累。两组材料来自不同实例和时间窗口，不能拼成同一个实例的连续时间线。

> 第一组案例为 10017 实例，Kvrocks 2.10.1、RocksDB 9.3.1，主要分析 metadata 列族，数据来自 2026 年 10 月 7 日的只读取证。第 8 节另行分析一组 2025 年 8–9 月的 RocksDB 9.3.1 日志。本文中的“小文件”如无特别说明，指小于 1 MiB 的 SST；MiB、GiB 均为二进制单位。

## 1. 先确认问题：增长的是文件数量

从 RocksDB 日志重建 metadata L6 的变化，可以看到文件数持续增长，而总字节数没有同步增长。

| 采样日期（日末或最后采样） | L6 文件数 | L6 大小 / GiB（约） |
|---|---:|---:|
| 09-29 | 292 | 30.47 |
| 09-30 | 344 | 30.79 |
| 10-01 | 401 | 30.32 |
| 10-02 | 461 | 29.35 |
| 10-03 | 528 | 28.57 |
| 10-04 | 625 | 29.12 |
| 10-05 | 875 | 33.38 |
| 10-06 | 1030 | 32.89 |
| 10-07 15:13 | 1155 | 30.19 |

在最后这一快照中，718 个文件小于 1 MiB，占文件数的 62.2%，但它们合计只有约 204 MiB，占 L6 字节数的 0.66%。文件大小中位数约 442 KiB。

目标 SST 大小配置为 128 MiB，并不意味着每个输出文件至少有 128 MiB。目标大小主要控制何时结束一个正常输出文件，其他切分条件、输入结束、记录过滤，都可能产生更小的文件。排查的关键是找到实际发生的那一条路径。

这里首先出现了一个线索：718 个小文件中，**688 个出生于 L5，占 95.8%**。因此，需要往上追踪它们的生成任务，再看它们如何进入 L6。

## 2. 请求较均匀，碎片却集中在两个 slot

业务通过同步程序复制源集群一个节点的写请求。当前请求形态是写入新的 String key，再设置过期时间：

```text
SET LK:<18 位数字 ID> <value>
PEXPIREAT LK:<同一个 ID> <过期时间>
```

业务 key 持续递增，TTL 统一约为 12 小时。这里“相同 TTL”指生命周期长度相同，不是所有 key 都在同一个绝对时刻过期。

为了确认是否存在 slot 热点，解析了 16 个已归档 WAL，合计约 887 MB，覆盖约十分钟量级的写入窗口：

| 指标 | 结果 |
|---|---:|
| metadata Put 次数 | 35,710 |
| 不同 key 数 | 17,855 |
| 请求 slot 范围 | 0–2729 |
| 实际覆盖 slot 数 | 2727 / 2730 |
| 平均每 slot 不同 key 数 | 6.54 |
| slot 498 的不同 key 数 | 5 |
| slot 1088 的不同 key 数 | 5 |

每个 key 恰好出现两次 metadata Put，与 SET 和设置过期时间的请求形式相符。将槽位等分成十段，每段 273 个 slot，各段不同 key 数为 1747–1841，接近平均值 1785.5。

但后续 MANIFEST 快照中，L6 的 737 个小文件有 626 个集中在 slot 498、1088，占 **84.9%**。这里的后续快照共有 1171 个 L6 文件，与前面的 1155 / 718 是不同时间的统计。

![请求槽位分布与 L6 小文件分布对比](l6-small-files-20261007/diagrams/03-request-vs-small-files.svg)

图 1：左侧是请求样本，右侧是存量小文件按起始 slot 分组的结果。二者时间跨度不同，不能据此计算写放大；但采样期没有显示与碎片集中位置对应的写入热点。

两个 slot 在样本中只占不同 key 数的 0.056%，却对应约 85% 的存量小文件。这个反差引导我们继续检查存储 key 的顺序和历史文件边界。

## 3. Slot 编码把递增写入分成了很多条追加序列

开启 cluster 模式、编码 slot 的情况下，Kvrocks metadata key 的主要布局为：

```text
namespace 长度 | namespace | slot（2 字节，大端序）| 业务 key
```

在同一个 namespace 内，先比较 slot，再比较业务 key。业务 key 是固定前缀加等长数字 ID，因此其字典序也对应 ID 的大小顺序。

![Kvrocks 集群模式下的 key 编码](key-encoding/kvrocks-cluster-key-encoding.svg)

图 2：本文重点关注图中的 metadata key。String 的内容随元数据保存在 metadata 列族中，这也是本次主要分析该列族的原因。

全局不断增加的 ID 经散列分散到多个 slot 后，每个 slot 内都形成一条向旧 ID 后方延伸的序列：

```text
slot 498：旧 ID …… 较新 ID …… 本轮新 ID
slot 499：旧 ID …… 较新 ID …… 本轮新 ID
slot 500：旧 ID …… 较新 ID …… 本轮新 ID
```

MANIFEST 中也有相应证据：slot 498 的 212 个完整位于该 slot 的 L6 文件，按 key 排序后，211 对相邻文件的创建时间全部不下降；slot 1088 的对应结果是 427 / 428 对。这支持较新 ID 持续追加在同 slot 旧 ID 后面的写入形态。

一次 L4+L5 合并，参与输入的未必包括这些旧 L6 数据。归并后的输出可能只有每个 slot 的少量新 ID，于是会从 slot 498 的新 ID，直接跳到 slot 499 的新 ID。中间虽然没有本轮待输出的记录，L6 中却可能存在完整的旧文件。

需要强调：这里看的是 **L4 与参与合并的 L5 文件归并后的输出顺序**。单个 L4 文件存在 key 跳跃，不代表最终输出一定跳跃；其他 L5 输入也可能填补中间的 key。L0 的单个 SST 内部同样有序，区别在于 L0 不同文件之间可以有重叠范围。

## 4. 提前切分为什么能省 IO，又为什么会留下小文件

对于 `L4 + L5 → L5`，RocksDB 会参考下一层 L6 的文件范围。这些 L6 文件在相关代码中称为 grandparents。

假设合并输出的相邻两个 key 为 m、s：m 位于 L6 文件之间的空隙，s 位于大文件 B 的范围内；它们之间还有一个完整的旧文件 A。

```text
输出 key：  m                           s
L6 范围：          [ A ]           [ B ───────── ]
```

如果将 m、s 写入同一个 L5 SST，这个 SST 的整体范围会跨过 A。以后它向 L6 合并时，就可能需要把 A 一并读入、重写，尽管本轮没有任何更新落在 A 的 key 范围内。

在 s 写入前切开，可以让左侧输出结束于 m，右侧输出从 s 开始。两边都避开 A，后续有机会省掉 A 的 IO；右侧输出仍与 B 重叠。

RocksDB 9.3.1 的 `CompactionOutputs::ShouldStopBefore` 中，这个分支的核心条件如下：

```cpp
const size_t num_skippable_boundaries_crossed =
    being_grandparent_gap_ ? 2 : 3;
if (compaction_->immutable_options()->compaction_style ==
        kCompactionStyleLevel &&
    num_grandparent_boundaries_crossed >=
        num_skippable_boundaries_crossed &&
    grandparent_overlapped_bytes_ - previous_overlapped_bytes >
        compaction_->target_output_file_size() / 8) {
  return true;
}
```

理解这段代码，需要分清三个量。

**第一，边界数统计的是从上一个输出 key 推进到当前候选 key 这一步跨过的边界。** 当前 key 落在某个 L6 文件范围内，门槛为 ≥3；落在文件间空隙中，门槛为 ≥2。例如“进入 A、离开 A、进入 B”是三个边界，“进入 A、离开 A、停在空隙”是两个边界。

**第二，大小条件统计的是这一步新计入的 L6 文件完整大小。** 它不是整个新 L5 文件从首 key 到当前 key 覆盖的累计大小。上一个 key 已经在 A 内、当前 key 进入 C，中间跨过 B，则新增计入的是 B+C，不重复计入 A。

**第三，新增大小不等于实际可省下的 IO。** 从空隙中的 m 出发，完整跳过 A，再进入 B，判断时会计入 A+B。即使 A 只有几 MiB，B 很大也足以使判断成立；未来可以避开的却只有 A。

本实例目标文件大小为 128 MiB，因此大小门槛是严格大于 16 MiB。这个分支没有要求“当前输出文件至少已经写入多少字节”。只要条件满足，哪怕当前文件只有一条记录，也会在写入下一条 key 前关闭。

![一次提前切分的边界计算与输出文件变化](l6-small-files-20261007/diagrams/02-l4-l5-early-split.svg)

图 3：提前切分发生在新 L5 文件的生成过程中。这里参考 L6 的边界，并没有在这一步直接拆分 L6 文件。

## 5. 把示意图落到真实文件：3185 B 的 #158375

2026 年 10 月 6 日 12:14:34，JOB 42980 执行 `1@L4 + 24@L5 → L5`。输入、输出均为 50,529 条记录，生成 29 个 SST。

其中 #158375 处于输出序列中间，只有 **3185 B、1 条记录**，key 属于 slot 498。下一个输出文件 #158376 从 slot 499 开始。

重放该任务提交前的 MANIFEST，可以还原以下布局：

| 角色 | 文件或 key | 范围 / 大小 |
|---|---|---|
| 已写入的 m | #158375 的唯一 key | slot 498；与当时 L6 无重叠 |
| 完整跳过的 A | #90521 | slot 499 旧 ID；3,109,364 B |
| 新进入的 B | #157811 | slot 499–509；134,465,913 B |
| 待写入的 s | #158376 的首 key | slot 499；落在 B 的范围内 |

从 m 推进到 s，进入 A、离开 A、进入 B，恰好三个边界。新增计入大小为：

```text
3,109,364 + 134,465,913 = 137,575,277 B
                           ≈ 131.2 MiB > 16 MiB
```

它满足前述分支的条件。由于 m 本身与 L6 无重叠，生成的小 SST 随后可以通过 trivial move 直接进入 L6。日志明确记录：

```text
2026/10/06-12:14:36.270290 ... Moving #158375 to level-6 3185 bytes
```

Trivial move 只更新文件所属层级，不读取并重写 SST。因此，它既不会顺便合并相邻小文件，也不会执行逐条过期过滤。

另外两个独立任务也重建出了相同路径：

| 小文件 | 生成 JOB | 大小 / 记录数 | 跨过边界数 | 后续行为 |
|---|---:|---|---:|---|
| #138312 | 37904 | 10,831 B / 3 | 3 | trivial move 到 L6 |
| #141587 | 38748 | 9,076 B / 3 | 3 | trivial move 到 L6 |
| #158375 | 42980 | 3185 B / 1 | 3 | trivial move 到 L6 |

三个任务都没有记录数减少，实际只有一个 subcompaction，输出无压缩。结合 #158375 位于输出中间的事实，可以排除这些样本由大量过期过滤、压缩、并行子任务尾部或整个任务最终余量产生的解释。

## 6. 最初没有那么多小文件，这个过程怎么开始

slot 498 和 slot 1088 后面，分别有一个长期保留的旧尾文件：

| 碎片集中的 slot | 下一 slot 的尾文件 | 生成时间 | 大小 |
|---|---|---|---:|
| 498 | slot 499 的 #90521 | 10-02 00:59:35 | 2.97 MiB |
| 1088 | slot 1089 的 #73132 | 09-30 19:09:01 | 1.78 MiB |

两者都来自普通 `1@L5 + 5@L6 → L6` 合并：依次生成五个约 128 MiB 的文件，输入结束时再留下一个小尾文件。这种尾文件本身是正常现象。

刚生成 #90521 时，前一个满文件 #90520 覆盖 slot 488–499。后续 compaction 又改变了周围文件的边界，才逐渐出现“slot 498 新 ID 在空隙中，后面紧接 slot 499 旧尾文件和大文件”的布局。不能把这两个时刻当成同一张快照。

早期样本 #95353 只有约 326 KiB，位于 slot 498，是所属任务的第一个输出文件。下一输出从 slot 499 开始，中间跨过 #90521，再进入约 128 MiB 的 #94998。这个早期小文件与当时 L6 无重叠，已经具备直接移入 L6 的条件。

slot 1088 也存在对应样本：#79606 大小 551,420 B，是任务第一个输出，后面跨过 #73132，再进入大文件 #78462。

这说明最初的小文件不依赖“前面已经有很多碎片”。任务恰好从某个 slot 的尾部开始，随后在下一 slot 前提前结束输出，就足以形成一个小文件。

![从正常尾文件到持续积累的 L6 碎片](l6-small-files-20261007/diagrams/01-l6-fragmentation-timeline.svg)

图 4：各阶段对应不同时间。少量历史尾文件提供了边界，后续切分和移动才逐步积累出大量碎片。

运行更久后，另一侧的切分条件也逐渐满足。进入 slot 498 的新 ID 之前，已经可以完整跳过一串同 slot 的旧文件：

| 新小文件生成时刻 | 前面完整跳过的旧文件数 | 总大小 |
|---|---:|---:|
| #138312，10-05 09:09 | 24 | 19.81 MiB |
| #141587，10-05 13:35 | 43 | 24.04 MiB |
| #158375，10-06 12:14 | 123 | 48.90 MiB |

这些总量均超过 16 MiB。于是，新数据进入 slot 498 前可以先切一次，离开 slot 498 时又因 slot 499 的尾文件和大文件再切一次。两次切分之间，只剩本轮 slot 498 的少量新 key。

新小文件进入 L6 后，又成为下一轮可跳过的旧文件之一。逐渐增长的是旧文件串的数量和累计大小，SST 本身不会原地长大。

## 7. 业务只有 12 小时 TTL，为什么文件还能一直留着

业务过期与 SST 物理回收是两个过程。

读请求可以判断 key 已过期并返回不存在；要让文件退出 LSM，仍需要删除、重写和过滤等实际回收过程。新 key 不断向后追加，旧范围很少被重新覆盖；提前切分又减少了后续合并对旧范围的重写，旧文件便更容易留存。

本例不只是根据文件年龄推测过期。对 #158375 的记录进行只读解析后，确认了以下时间：

| 项目 | 时间或结果 |
|---|---|
| SST 创建时间 | 10-06 12:14:35 |
| 记录中存储的过期时间 | 10-07 00:13:39.472 |
| 检查时已过期 | 约 16.5 小时 |
| 在线 PTTL / TYPE | -2 / none |
| 文件是否仍在 L6 | 是 |

后续快照中的 737 个小文件，有 598 个创建已超过 12 小时，506 个超过 24 小时。文件年龄不能证明全部记录都过期，但 #158375 提供了“业务已过期、物理文件仍留存”的直接样本。

当时 OPTIONS 中 `ttl` 和 `periodic_compaction_seconds` 均为 30 天。RocksDB 的这些文件级 compaction 参数与 Redis key 的 12 小时 TTL 不是同一个概念。常规 leveled compaction 也不会仅因 L6 小文件数量增多，就自动将它们聚合。

## 8. 当 L6 积累到 50 万个文件：从版本更新变慢到写入降速

前面的实例说明了小文件如何形成、为什么长期留存。另一组实例的 12 份滚动 LOG，则记录了这种文件布局达到更大规模后的运行状态。日志保存在 `temp/db`，主要数据活动覆盖 2025 年 8 月 20 日至 9 月 3 日。

这组材料没有 MANIFEST、SST 或 WAL，因此不能还原每个文件的 slot 范围，也不能证明每个小文件都由前述提前切分分支产生。它能直接确认的是：大量小文件在上层生成后移入 L6，文件数量和活跃 SST 容量持续增长，单文件移动的提交阶段明显变慢，随后出现容量积压及写入反压。

### 8.1 文件数持续增长，随后 L5 也开始积压

| 日期（日末或最后采样） | L6 文件数 | L5 文件数 | metadata 活跃 SST / GiB |
|---|---:|---:|---:|
| 08-20 | 144,418 | 564 | 172.30 |
| 08-24 | 230,419 | 588 | 223.34 |
| 08-29 | 411,403 | 1,026 | 426.74 |
| 08-31 | 456,276 | 5,058 | 516.93 |
| 09-01 | 478,684 | 26,461 | 571.59 |
| 09-02 | 499,444 | 54,189 | 627.77 |

与第一组实例不同，这次不仅文件数增长，活跃 SST 的总字节数也明显增长。这里的容量来自文件事件重建，并由日志层级统计交叉核验；它不是文件系统 `df`，不包含 WAL、LOG、MANIFEST、备份等占用。

09-03 06:01，日志直接报告 L6 有 **509,543 个文件、566.42 GiB**，平均每个文件约 **1.14 MiB**，远低于 128 MiB 的目标大小。L5 则已有 59,226 个文件、70.47 GiB。

在稍早的 09-03 00:20 快照中，L6 共 500,011 个文件，其中 384,231 个能从保留日志追溯大小：220,837 个小于 1 MiB，382,848 个小于 16 MiB。因此，即使不推测其余文件，也能确认 **至少 76.57% 的全部 L6 文件小于 16 MiB**。已追溯子集中，97.04% 的文件最初生成在 L5。

### 8.2 不重写 SST 的 trivial move，也逐渐需要数秒

Trivial move 不读取和重写 SST 内容，但仍需要提交文件所属层级的变化，并发布新的版本状态。RocksDB 9.3.1 中相关执行顺序为：

```text
Moving #... 日志
    → VersionSet::LogAndApply
    → InstallSuperVersionAndScheduleWork
    → trivial_move 事件
```

按后台线程匹配起止记录，只统计 metadata 列族、单文件、目标为 L6 的移动，共得到 413,226 个有效样本。对于缓冲输出的日志，使用其中的 `Original Log Time`，避免把缓冲日志的输出延迟算进去。

| 日期 | 样本数 | 平均耗时 | 中位耗时 | P99 耗时 |
|---|---:|---:|---:|---:|
| 08-20 | 19,609 | 0.249 秒 | 0.248 秒 | 0.280 秒 |
| 08-24 | 24,024 | 0.436 秒 | 0.434 秒 | 0.470 秒 |
| 08-28 | 40,173 | 0.743 秒 | 0.737 秒 | 1.200 秒 |
| 08-30 | 26,334 | 1.175 秒 | 0.888 秒 | 3.285 秒 |
| 08-31 | 21,715 | 2.085 秒 | 1.903 秒 | 3.615 秒 |
| 09-01 | 22,752 | 3.140 秒 | 3.745 秒 | 4.124 秒 |
| 09-02 | 21,709 | 4.737 秒 | 4.784 秒 | 5.649 秒 |
| 09-03，主要为清理前 | 17,464 | 5.247 秒 | 5.211 秒 | 5.940 秒 |

后期平均值和中位数都达到数秒，说明高耗时已相当普遍。09-02 约一半样本至少需要 4.78 秒，而不是只有极少数慢任务抬高了平均值。耗时恶化在 8 月底已经明显，早于 09-01 首次可见的 pending 降速。

这个时间区间包含版本构建、MANIFEST 提交、锁与队列等待、版本安装和线程调度，不能当作某个函数的纯 CPU 耗时。但它证明了：**即使省掉 SST 数据重写，后台推进文件仍可能付出很高的提交成本。**

### 8.3 为什么只移动一个文件，也受几十万个文件影响

这里的 Version 指一个列族当前各层的 SST 集合、范围和相关索引。旧读请求可能仍持有旧 Version，RocksDB 会构建新的 Version，再供后续请求使用。

例如，将 X 从 L5 移到 L6，逻辑变更只有“L5 删除 X、L6 添加 X”。但新 Version 仍需要描述这个列族的完整文件布局。现有 `FileMetaData` 对象可以共享，新版本的文件列表及派生结构却仍有大量构建工作：

| RocksDB 9.3.1 中的步骤 | 与文件数量的关系 |
|---|---|
| `VersionBuilder::SaveSSTFilesTo` | 遍历已有文件，与新增文件合并，排除删除项，生成新版本各层的文件列表；排序对象是新增文件，并非重新排序全部旧文件 |
| `DoGenerateLevelFilesBrief` | 逐文件生成范围条目，分配内存并复制 smallest/largest key |
| `GenerateFileLocationIndex` | 遍历所有层的文件，建立“文件编号 → 层级、位置”的索引 |
| 层容量和 compaction 相关计算 | 遍历文件累计大小、计算相邻层重叠等；例如 L5 的重叠优先级计算也需要参考 L6 |

因此，拥有 50 万个 L6 文件时，一次很小的变更也可能伴随多轮几十万条文件元数据的处理，消耗 CPU、内存带宽、缓存及内存分配资源。旧 Version 最终释放时，同样要遍历它持有的文件并减少引用计数。

这不只影响 L5→L6。同一列族的 L4→L5、L1→L2，甚至 flush 完成后把新 L0 文件加入布局，都可能承担大文件集合下的版本构建成本。其他列族不需要重建这个列族的文件集合，但同一个 DB 的 MANIFEST 提交队列仍可能带来跨列族等待。

`LogAndApply` 的提交者进入 `manifest_writers_` 队列，后续提交需等待前面的处理，部分变更可以合并提交。文件多既可能增加处理任务的数量，也会提高单次版本更新的成本；存在串行提交环节时，增加后台线程无法让这部分吞吐量按比例提升。

需要区分 **MANIFEST 记录写入** 与 **新 Version 的构建和发布**：普通提交通常只追加增量 `VersionEdit`，并不会每次把全部 50 万个文件的信息重新写进 MANIFEST。上述全量处理主要发生在内存中的文件集合和索引构建。仅凭日志时间差，不能把慢的原因直接归为 MANIFEST 写盘。

源码机制和耗时趋势共同支持“大量 SST 是版本处理成本上升、后台下沉能力下降的重要因素”。但本次没有 CPU profile、锁等待和磁盘延迟采样，不能断言后期的 5 秒全部消耗在文件遍历，也不能排除后台配置变化、IO 和调度的共同影响。其他类型任务是否同样达到数秒，仍需要分别计时。

### 8.4 直接触发降速的是容量积压，不是文件数

`estimated pending compaction bytes` 估计的是消化当前层级容量积压所需的合并工作量，不是“小文件个数 × 固定成本”，也不是“L6 总大小”。估算会考虑上层超出目标的字节数、向下传递的积压，以及下一层参与合并的放大。

该实例使用动态层容量，层级比例为 10。09-03 06:01，L6 约 566.42 GiB，对应 L5 目标容量约 56.64 GiB；L5 实际已有 70.47 GiB，还要承接更上层预计下沉的数据。按日志展示的层容量近似复算，pending 约 163.09 GiB，与日志直接报告的 **163.17 GiB** 接近，其中主要贡献来自 L5→L6。

软阈值为 64 GiB，硬阈值为 256 GiB。日志记录了完整的反压升级过程：

| 时间 | 日志事实 |
|---|---|
| 09-01 15:15:28 | 首次可见 pending 降速，pending 约 65.99 GiB，超过软阈值 |
| 09-02 12:06:35 | 动态写入限速已降到 16 KiB/s |
| 09-02 14:02:23 | pending 超过 256 GiB，出现 `Stopping writes` |
| 09-02 16:08:39 | pending 达到窗口内峰值 257.77 GiB |

本例配置的 `delayed_write_rate` 上限虽然很高，仍不能关闭积压驱动的动态反压。写入限速会随积压变化逐步降低，超过硬阈值则可能停止写入。调高写入速率上限并不能消除后台积压。

这些证据支持以下解释：

```text
大量小 SST 长期留存
    → 文件集合膨胀，版本构建与提交成本增加
    → compaction 完成、安装结果和继续推进的能力下降
    → 持续写入下，上层容量逐渐积压
    → estimated pending compaction bytes 超限
    → 写入降速，严重时停写
```

写请求在存储层等待，会增加该实例的写入响应时间；如果同步程序、代理或批量请求需要等待该节点，也可能把影响传递到更大范围。但这组 LOG 没有客户端延迟数据，不能据此量化整个集群的响应时间变化。

日志也没有磁盘满错误。这里直接确认的降速触发器是 pending 超限，不能写成“磁盘使用率达到某个百分比后限速”。

### 8.5 清理结果说明了什么，又不能说明什么

09-03 08:46 左右开始一系列 manual compaction。输出至 L6 的 342 个手工任务合计输入 606.34 GiB、输出 77.88 GiB，输入记录数从约 3018 万减少为约 391 万，减少约 87.06%。这是任务汇总，不等于去重后的物理磁盘回收量；日志也不能逐条区分 TTL 过期和其他记录清理原因。

09:24:56，最终活跃文件状态为：

```text
L6 文件数：1153
metadata 活跃 SST：78.55 GiB
estimated pending compaction bytes：0
```

实际重写确实回收了大量文件和内容。但清理中间还有一个更能解释 pending 的状态：**08:49:38，L6 仍有 516,485 个文件、L5 仍有 50,808 个文件，pending 已经为 0。**

这说明文件数量带来的处理成本与按字节计算的容量压力是两个指标。容量压力可以先缓解，而大量文件的管理成本仍然存在；pending 为 0 不代表碎片已经消失。

日志最后一次 flush 在 08:46:30，清理后缺少持续相同写入负载下的对照。因此，可以确认文件数、活跃容量和 pending 显著下降，尚不能声称已验证同等负载下 trivial move 耗时或集群延迟恢复。

## 9. 用 periodic compaction 规避长期积累

我此前在 [PR #3170](https://github.com/apache/kvrocks/pull/3170) 中增加了 RocksDB periodic compaction 的配置入口，对应上游提交为 [`4025a6d2`](https://github.com/apache/kvrocks/commit/4025a6d23698b6bd5383511f259d10988fe7dc0e)，提交标题是 `feat(config): add RocksDB periodic compaction controls`。

这个提交把 RocksDB 已有的能力接入 Kvrocks，增加了三个配置项：

| 配置 | 作用 |
|---|---|
| `rocksdb.periodic_compaction_seconds` | 按文件年龄触发周期合并，让长期未重写的 SST 有机会重新经过 compaction filter |
| `rocksdb.ttl` | RocksDB 的文件年龄相关 compaction 配置，不是业务 key 的 TTL |
| `rocksdb.daily_offpeak_time_utc` | 为周期合并提供 UTC 低峰时间窗口，允许部分即将到期的文件提前参与调度 |

本例真正需要的是让旧 L6 文件重新经过过滤。RocksDB 9.3.1 的 periodic compaction 候选范围包括最后一层；L6 文件被选中后，在 L6 内进行实际重写。同层 compaction 不能通过 trivial move 完成，因此会给 Kvrocks 的 `MetadataFilter` 执行过期检查的机会。

### 为什么“递增 key + 相同 TTL”在这里尤其有效

这两个业务特征使文件的 key 范围和记录的时间关系较为一致。

递增 key 让同一 slot 内较旧的数据位于前面，新数据通常落在后面，旧的小 SST 很少持续混入新的记录。相同 TTL 则让同一批次记录的过期时间随写入时间一起后移。如果一个小 SST 保存的只是一个较短时间段的写入，那么经过足够时间，文件中的记录就可能全部过期。

例如，一批记录写入于 00:00–00:10，另一批写入于 01:00–01:10，TTL 都是 12 小时。它们分别在 12:00–12:10 和 13:00–13:10 到期。到了 13:30，只要旧 SST 里的记录没有被续期，这两批就都已过期。

这时即使 periodic compaction 一次只重写一个小 SST，过期过滤也可能把其全部记录丢弃，使原 SST 从活跃版本中移除，不再留下承载这些记录的新 SST。减少文件数并不一定需要先把多个小文件合成一个大文件。

![递增 key 和统一 TTL 下周期合并的回收过程](l6-small-files-20261007/diagrams/04-periodic-compaction-ttl.svg)

图 6：示意同一 slot 内不同写入批次的过期关系。图中的观察时间不是 periodic compaction 的精确调度时间；实际调度依据文件年龄、周期配置和后台资源。

因此，这个方案对本例的价值是：**持续产生的新文件可以保留，已经过期的旧碎片则持续退出 L6，让文件数量不再随着历史写入无限积累。** 冷范围不必等到恰好有重叠写入才被清理。

提前切分条件本身仍可能满足，新的小文件也仍可能产生。Periodic compaction 针对的是它们的留存时间，还可能通过回收旧尾文件、旧碎片串改变后续切分所依赖的边界。它不是对 `ShouldStopBefore` 的修改，也不保证把仍然有效的相邻小文件合成大文件。

### 如何选择周期，以及如何判断它是否有效

对于统一 12 小时 TTL 的业务，可以把 12 小时至一天作为评估周期的起点。例如，在已经包含该配置入口的版本中，以下是一日周期的配置示例：

```conf
rocksdb.periodic_compaction_seconds 86400
```

这不是“每到固定时刻全库合并一次”，也不保证 key 过期后立即回收。它按 SST 年龄产生候选，后台仍需要安排任务；已有 backlog、文件重写时间和低峰调度也会影响实际回收时刻。这个参数也不能只看业务 TTL 就机械设定，需要结合 IO 预算和可接受的物理留存时间。

如果需要利用 `rocksdb.daily_offpeak_time_utc`，应按 UTC 配置并核对当地时间。它用于影响周期合并的调度，不是所有 compaction 只能在该窗口执行的硬限制。

验证时应同时观察：

- 日志中是否出现 `PeriodicCompaction`，旧 L6 文件是否实际被重写、删除。
- 已过期的小 SST 是否持续退出活跃文件集合，小文件数量是否从长期增长转为在一定范围内波动。
- compaction 读写量、后台积压和业务延迟是否在可接受范围内。
- 单文件 trivial move 的提交耗时、各层文件数和字节数是否持续恶化；不能只凭 pending 暂时为 0 判断文件管理成本已经可控。

第二组实例也提醒我们，配置了周期并不代表回收足够及时：它的周期同样是 30 天，保留日志内实际出现过 9269 个 metadata `PeriodicCompaction` 任务。但大部分新碎片在可见积累窗口内尚未达到这个年龄门槛，常规容量 compaction 积压后也会优先占用调度机会。因此，应在碎片尚未形成巨大积压时验证回收节奏，不能把周期合并当成已有 50 万文件后的即时清理保证。该实例没有调整为更短周期后的对照结果。

这套思路依赖本例的业务条件：key 持续递增、较少重复更新和续期、TTL 相近，旧文件中的记录能够逐步全部过期。如果同一个文件长期混有永久 key、不同生命周期的数据或不断续期的记录，周期合并仍可能留下小文件。后台清理能力也必须跟得上产生速度。

本次取证没有在线修改周期配置，也没有做修改前后的运行对照，因此这里给出的是基于源码与业务分布的规避方案，不把预期效果写成已经完成的生产验证。原实例的版本、默认 30 天周期和上述配置入口是否已回移到部署二进制，也应在落地前核对。

## 10. 这些案例说明了什么

这次排查中，一项减少未来重叠 IO 的优化，遇到了按 slot 分段、不断追加新 ID 的写入形态。少量历史尾文件提供了可跳过的边界，上层合并因此反复切出小 SST；无重叠的文件原样移入 L6，又因缺少及时重写而持续留存。旧碎片串积累之后，进一步增强了两侧切分条件。

单看文件大小配置、slot 请求数量或业务 TTL，都不足以解释这个现象。把请求编码、合并输出顺序、文件生命周期和过期回收放在一起，才能看到完整链路。

第二组日志进一步展示了碎片的运行成本：L6 的大量文件不仅占据空间和文件管理资源，还使本来不重写数据的 trivial move 也变得昂贵。结合版本更新源码，这支持文件数量膨胀降低后台处理能力的判断；上层按字节计算的积压随后触发了可直接观察到的写入降速和停写。不能把两者简化成“文件多就直接触发 pending 阈值”，也不能把所有耗时都归为 MANIFEST 写盘。

对于这个具有统一 TTL 的递增写入场景，periodic compaction 提供了另一条回收通道：旧数据即使不再被更新，也能重新经过过滤，让已过期的小文件退出 L6。这是利用业务数据的时间规律，限制碎片持续累积的一种方式。
