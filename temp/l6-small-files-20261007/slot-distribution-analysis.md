# 请求槽位均匀性与碎片形成历史

对象：10.148.7.45:10017。分析日期：2026-10-07。
用户确认请求由同步程序从源集群一个节点复制而来，并撤回了最初提供的 2730–5459 范围。扩大样本实际核验的请求范围是 **0–2729**；前文“0–2730”是近似表述，以本次精确统计为准。

结论：本次约十分钟量级窗口内，新增 key 的 slot 分布与均匀散列相容，slot 498、1088 没有请求数量热点。碎片集中主要与特定历史文件边界有关。两个位置都能追溯到下一 slot 留下的独立 L6 尾文件；它们与后面的正常大小文件一起，使前一 slot 的新数据容易被切开。之后同一 slot 的旧碎片累积超过切分阈值，又增强了进入该 slot 前的切分条件。

SST 文件生成后不可变，不会在原文件内持续追加变大。随运行时间变化的是后续 compaction 生成的替代文件、文件边界以及一组文件的累计大小。

**两个固定边界最初怎样出现**

日志与 MANIFEST 给出了如下历史：

| 前一 slot 的碎片位置 | 下一 slot 中保留的尾文件 | 生成时间 | 生成任务 |
|---|---|---|---|
| 1088 | #73132，slot 1089，1,867,276 B，80 条记录 | 09-30 19:09:01 | JOB 21156 |
| 498 | #90521，slot 499，3,109,364 B，140 条记录 | 10-02 00:59:35 | JOB 25795 |

两个任务都是普通的 `1@L5 + 5@L6 → L6`，只有一个 subcompaction，无压缩。输出均是：

```text
约 128 MiB + 约 128 MiB + 约 128 MiB + 约 128 MiB + 约 128 MiB + 一个小尾文件
```

#73132 与 #90521 就是最后的小尾文件。这是普通 compaction 的剩余输出。它们本身分别只有约 1.78 MiB、2.97 MiB，未超过 16 MiB 的 skippable-grandparent 大小门槛，但后续判断还把新进入的约 128 MiB 文件计入增量，因此仍会触发。

旧小尾文件长期保留，后面的较大文件随普通 compaction 不断被替换。比如 #90521 后面在不同时间对应 #136712、#140088、#157811；它们一直在约 128 MiB 附近。这条证据不支持“某个原有 SST 逐渐原地长大才发生问题”，而是支持“稳定的小尾文件边界 + 后面的大文件”持续满足条件。

注意：尾文件刚生成时，前一个约 128 MiB 文件仍可能跨到同一个 slot。不是尾文件出现就立即保证前一 slot 所有新 key 都处于无重叠空隙；后续 compaction 对边界的调整、任务的输入范围也参与了碎片的初次生成。

**早期的小文件已经能复现同一切分**

MANIFEST 重放至这些 L5 文件生成前：

- #79606：10-01 06:02:16，slot 1088，551,420 B，是该任务的第一个输出文件。它之后的输出从 slot 1089 开始，跨过 #73132，再进入 #78462（134,390,900 B）。该小文件与当时 L6 无重叠。
- #95353：10-02 09:50:17，slot 498，334,315 B，也是该任务的第一个输出文件。下一输出从 slot 499 开始，跨过 #90521，再进入 #94998（134,405,660 B）。同样无 L6 重叠。
- #96465：10-02 11:35:27，slot 498，227,057 B，重复了同样的形态。

这些早期任务本身就从 slot 尾部开始，不必先假设左边已经有大量碎片；在下一 slot 前提前结束第一个输出，就能产生最初的小文件，并允许它直接移入 L6。

这种条件并不要求某个 slot 的请求数量更多。均匀写入分散到 2730 个 slot 后，单个任务在一个 slot 尾部仍可能只有少量数据。

**为什么运行越久越容易持续积累**

后期不仅有“在 slot 498 结束后切一刀”，还出现“在 slot 498 开始前也切一刀”。

以 #158375 所属任务为例：

```text
L5 合并的输出顺序：
slot 497 的新 key → slot 498 的新 key → slot 499 的新 key

L6 中夹在这些新 key 之间的旧文件：
                 [slot 498 旧文件串]
                                          [slot 499 小尾文件 A] [大文件 B]
```

当输出从 slot 497 跳到 slot 498 的新 ID 时，已经能完整跳过 slot 498 的旧文件串。按三个历史样本重建：

| 新小文件 | 生成时间 | 前面完整跳过的旧文件数 | 合计字节数 |
|---|---|---:|---:|
| #138312 | 10-05 09:09 | 24 | 20,772,209 B，约 19.81 MiB |
| #141587 | 10-05 13:35 | 43 | 25,208,491 B，约 24.04 MiB |
| #158375 | 10-06 12:14 | 123 | 51,278,768 B，约 48.90 MiB |

它们都超过 128 MiB / 8 = 16 MiB，边界数也满足条件。因此：

1. **进入 slot 498 的新数据前切开**：跳过已有旧文件串，累计大小超过 16 MiB。
2. **离开 slot 498 时再切开**：跳过 slot 499 的旧尾文件，并进入后面的约 128 MiB 大文件。
3. 两刀之间只剩本轮 slot 498 的少量新 key，形成独立小 SST。
4. 新 ID 的范围与旧 L6 文件无重叠，于是直接移入 L6。
5. 它成为下一轮可跳过的旧文件之一，增加旧文件串的数量和总大小。

这是一种正反馈：早期可以偶发地从任务开始位置或其他切分位置产生小文件；旧文件累积后，两侧切分条件更容易同时满足，反复隔离出同一 slot 的新数据。

对应位置在 [9.3.1 compaction_outputs.cc](../rocksdb-9.3.1/db/compaction/compaction_outputs.cc) 的 UpdateGrandparentBoundaryInfo 与 ShouldStopBefore。切分阈值检查的是新计入的 grandparent 总字节数，没有要求当前输出文件也必须达到某个最小大小。

**对“大文件变大”的判断**

后面的文件越大，确实越容易使“新计入的 grandparent 字节数 > 16 MiB”成立，这部分直觉是正确的。但本例更精确的说法是：

- 后面约 128 MiB 的文件早已足够超过门槛，无需继续变大。
- 独立的小尾文件增加了可跳过的边界，让从前一 slot 到下一 slot 的 key 跳跃能够触发该优化。
- 前一 slot 的旧碎片总量越积越多，又满足了另一侧的切分条件。
- 真正使现象稳定集中的，是这组历史边界与递增 ID 写入模式，而不是两个 slot 的请求量偏大。

其他位置也已有碎片，例如 slot 1827、2432。498、1088 不是算法写死的特殊 slot；它们当前拥有更早形成并长期保留的相关布局。此次没有逐个追踪所有 slot，不能断言每处碎片的历史都完全相同。
