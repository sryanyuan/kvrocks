# 10017 请求模式与 L6 小文件积累

检查时间：2026-10-07 16:30–16:45 左右（Asia/Shanghai）。
目标：10.148.7.45:10017，Kvrocks 2.10.1，Git dc4d5303，RocksDB 9.3.1。

结论：该实例当前的写入形态，是不断写入带 18 位数字 ID 的 String key，再设置约 12 小时 TTL。真实存储 key 按 namespace、slot、业务 key 排序；新 ID 在各 slot 内向后追加。在特定 slot 的尾部，前一轮确认的 grandparent 边界切分反复隔离出少量新 key，随后直接移入 L6。旧文件没有被重写，过期记录和小文件继续保留。因此，请求模式、slot 排序、当前 L6 文件边界与过期清理时机共同解释了此实例的问题。

这是对当前实例的机制解释，没有对照其他实例做实验，不能声称只有 10017 会出现，也不能仅凭请求判定客户端程序名称。

**为什么这些请求会在特定位置留下小文件**

从 MANIFEST 解码真实 metadata key，格式为：

```text
namespace | slot（2字节） | LK:<18位数字ID>
```

已对选定 key 重新计算 Redis CRC16 slot，结果与解码的 slot 一致。该实例开启 cluster 模式；CLUSTER NODES 显示本节点拥有 0–16383 全部 slot。因此，这里的 slot 是存储排序的一部分，并不意味着本节点只拥有某几个 slot。

新的 ID 与旧文件的 ID 顺序有直接证据：

- 实时采样的 71 个 ID 均大于快照中 slot 498、1088 所有小文件的最大 ID。
- slot 498 中 212 个完全落在该 slot 的 L6 文件，按 key 排序后，211 对相邻文件的创建时间全部不下降。
- slot 1088 的 429 个同类文件，428 对相邻文件中 427 对创建时间不下降。

这支持“较新的 ID 不断追加在同一 slot 的旧 ID 后面”，而不是反复覆盖同一批 key。短时采样不能保证每一个历史写入都如此。

当前 MANIFEST 快照里，metadata L6 有 1171 个文件，其中 737 个小于 1 MiB；和较早报告的 1155 / 718 是不同时间快照。

| 小文件所在 slot | 小于 1 MiB 的文件数 |
|---|---:|
| 1088 | 421 |
| 498 | 205 |
| 2432 | 34 |
| 1827 | 26 |
| 其他 | 51 |
| 合计 | 737 |

slot 498 与 1088 合计 626 个，约占 84.9%。这表示碎片集中在特定存储边界，不能等同于业务对这两个 slot 有相同比例的写入热点。

把前一轮抽象的 m、A、B 对应到真实数据：

```text
本轮 L5 合并中的新 key：
slot 498 的新 ID（m） → slot 499 的新 ID（s）

L6：
[slot 498 的一串旧 ID 文件]
                                 [slot 499 的旧 ID 文件 A]
                                                         [slot 499 较新 ID ... slot 510 的大文件 B]
```

对于 #158375：

- 它的唯一 key 属于 slot 498。
- 被跳过的 A 是 #90521，完全处于 slot 499，大小 3,109,364 B。
- 下一条输出 key 进入 B（当时是 #157811），约 128 MiB。
- 这触发提前切分；#158375 被单独留在 slot 498 的尾部，再 trivial move 到 L6。
- 后续 ID 更大，下一批又可以在已有文件后面形成一个新的、不重叠的小文件。

最新边界中，slot 498 的文件串后面仍是 #90521，再后面是一个从 slot 499 延伸到 510 的约 128 MiB 文件。slot 1088 也有类似形态：其文件串后面是 slot 1089 的 #73132（1,867,276 B），然后是约 128 MiB、跨 slot 1089–1100 的大文件。现有边界形态解释了为什么碎片特别集中在这两个 slot；slot 1088 未逐个重放每个小文件的生成分支，应与已详细验证的 slot 498 样本区别看待。

即使全局写入量不低，分散到许多 slot 后，一次 compaction 在某一个 slot 尾部只可能剩少量 key。分支没有最小输出大小门槛，就能把这部分单独切出来。实际出现 3185 B、1 条记录，正是这个极端例子。

**12 小时 TTL 为什么没有让小文件及时消失**

业务过期与 SST 物理回收是两件事。过期时间影响 key 是否可读；文件要通过实际重写/过滤等机制回收。trivial move 不读取并过滤记录，因此不会顺便清理过期数据。

此次额外只读检查了 #158375 的 3185 字节 SST，解析首条记录的 metadata 头部，核对内部 key 与 MANIFEST 一致，未导出业务 value 内容：

| 项目 | 结果 |
|---|---|
| 类型 | String |
| SST 创建时间 | 2026-10-06 12:14:35 |
| 记录中存储的过期时间 | 2026-10-07 00:13:39.472 |
| 检查时已过期 | 约 16.5 小时 |
| SST 是否仍在 L6 | 是 |
| 在线 PTTL / TYPE | -2 / none |

这直接证明了一个“业务已过期、物理 SST 仍留存”的样本，不只是根据文件年龄推测。

另在 slot 498、1088 分别选取从旧到新的 5 个小文件，检查首 key：每组较老的 4 个都返回 PTTL=-2，最新的 1 个仍有约 11 小时 TTL。PTTL=-2 本身只能说明该 key 当前不可读，不能单独区分过期与删除；只有 #158375 进一步核对了 SST 中的过期时间。

737 个小文件中有 598 个创建已超过 12 小时、506 个超过 24 小时。文件年龄不是所有内容都已过期的证明，但说明这些碎片具有持续留存特征。

RocksDB OPTIONS 的 ttl 和 periodic_compaction_seconds 都是 30 天，远长于观察到的业务 12 小时 TTL；两者也不能混为一谈。底层缺少按小文件数量进行聚合的触发条件，加上避免重叠的切分让冷范围少被重写，物理回收容易落后于业务过期。

**建议的下一步**

1. 复现应保留本实例的关键形态：开启 slot 编码、LK 加递增 ID、分散 slot 的新增写入、约 12 小时 TTL，以及 slot 尾部的小 L6 文件和下一 slot 的大文件边界。仅随机覆盖固定 key 集合的压测，可能无法复现。
2. 小文件生成侧继续优先验证 skippable-grandparent 分支的最小输出大小/实际可跳过字节收益条件。SET 改为带 PX 的 SET 可能减少一次写操作，但不改变递增 ID 与 slot 边界，不能保证解决碎片。
3. 存量清理可评估低峰对 bottommost 的真正重写，并以 slot 498/1088 对应范围做可控验证。预期同时验证文件数下降与过期数据回收，注意业务期间的 IO 和延迟。
4. 周期性过期清理策略需要与业务 TTL 匹配，但调小 periodic_compaction_seconds 不等于保证把相邻小文件合并。对单个 SST 重写与跨多个相邻 SST 合并应分别验证。
5. 若要继续确定请求由哪个同步任务产生，需要定位 172.24.65.199 上的客户端程序；目前只能确认来源地址与请求形式。

此次没有修改配置、执行写入、触发 compaction 或全库扫描。除一次已结束的短时 MONITOR 外，使用 INFO、CLIENT LIST、CLUSTER NODES、CONFIG GET、已有 SLOWLOG、少量 PTTL/TYPE，以及对日志、MANIFEST 和一个极小 SST 的只读检查。保存的证据不包含密码、完整业务 key 或业务 value。
