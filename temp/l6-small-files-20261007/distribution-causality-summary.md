# 10017 实例：数据分布与 L6 小文件的证据链

对象：`10.148.7.45:10017`，目录 `/data3/docker/volumes/10.148.7.45_10017/db`。
版本：Kvrocks 2.10.1，RocksDB 9.3.1。取证日期：2026-10-07；整理日期：2026-10-08。本文复核已有本地证据，没有重新连接实例；以下统计不代表 10 月 8 日的实时状态。

现有证据强烈支持：**按 slot 排序的递增 ID 写入，遇到特定历史 L6 文件边界后，使 L4+L5→L5 的提前切分反复隔离出少量新 key；这些小 SST 再原样移入 L6，并长期积累。** 请求采样没有显示 slot 498、1088 的写入热点，但它们占小文件数量的约 85%。具体切分分支是根据日志、MANIFEST 和对应版本源码重建的，日志没有直接打印分支名称；不能把样本验证表述为逐个证明全部小文件都由同一分支产生。

**1. 请求分布：slot 较均匀，业务 key 持续向后追加**

只读解析 16 个归档 WAL，合计 886,786,871 B。文件最后写入时间覆盖 10 月 7 日 16:50:27–17:00:24，首文件包含此前写入，因此是约十分钟量级窗口。

| 指标 | 结果 |
|---|---:|
| metadata Put 次数 | 35,710 |
| 不同业务 key | 17,855 |
| key 形式 | 全部为 `LK:<18 位十进制数字 ID>` |
| 每个 key 的 Put 次数 | 恰好 2 次，与 SET + PEXPIREAT 对应 |
| 请求 slot 范围 | 0–2729 |
| 实际覆盖 slot 数 | 2727 / 2730 |
| 平均每 slot 不同 key 数 | 6.54 |
| slot 498 / slot 1088 | 各 5 个不同 key，各 10 次 Put |
| 两个 slot 合计占不同 key 数 | 0.056% |
| 两个 slot 合计占 metadata Put 字节数 | 约 0.130% |

将请求槽位等分成 10 段，分布如下。字节数为 metadata Put 编码记录的统计，不是网络流量或 SST 大小。

| slot 范围 | 不同 key 数 | metadata Put 大小 / MiB |
|---|---:|---:|
| 0–272 | 1806 | 85.56 |
| 273–545 | 1780 | 83.24 |
| 546–818 | 1815 | 84.82 |
| 819–1091 | 1758 | 83.91 |
| 1092–1364 | 1841 | 92.32 |
| 1365–1637 | 1767 | 83.21 |
| 1638–1910 | 1750 | 82.58 |
| 1911–2183 | 1747 | 82.22 |
| 2184–2456 | 1772 | 85.10 |
| 2457–2729 | 1819 | 80.40 |

各段不同 key 数相对平均值的偏差约为 -2.2% 至 +3.1%，没有与碎片集中位置对应的明显请求数量偏斜。短窗口不能证明所有历史时段均匀。

从 MANIFEST 解码的 metadata key 按 `namespace | slot（2 字节）| 业务 key` 排序。编码 slot 与 Redis CRC16 重新计算结果一致。以下事实支持新增 ID 追加在旧 ID 后面的写入形态：

- 实时采样的 71 个 ID，均大于保留快照中 slot 498、1088 小文件的最大 ID。
- slot 498 有 212 个完全位于该 slot 的 L6 文件；按 key 排序后，211 对相邻文件的创建时间全部不下降。
- slot 1088 有 429 个同类文件；428 对相邻文件中，427 对创建时间不下降。

这说明较新的文件通常保存较后的 ID。此处的“追加”是逻辑 key 顺序；SST 创建后不可变，不会原地追加长大。实际是否出现跳跃，取决于 L4 与参与合并的 L5 文件归并后的输出序列，不能只看单个 L4 文件。

**2. L6 分布：字节数相近，文件数持续增长并集中在两个 slot**

较早快照截至 10 月 7 日约 15:13，metadata L6 有 1155 个文件、约 30.19 GiB。其中 718 个文件小于 1 MiB，合计仅占 L6 字节数的 0.66%，却占文件数量的 62.2%。文件大小中位数为 452,666 B，最小为 3185 B。

| 日期（日末或最后采样） | metadata L6 文件数 | 总大小 / GiB（约） |
|---|---:|---:|
| 09-29 | 292 | 30.47 |
| 09-30 | 344 | 30.79 |
| 10-01 | 401 | 30.32 |
| 10-02 | 461 | 29.35 |
| 10-03 | 528 | 28.57 |
| 10-04 | 625 | 29.12 |
| 10-05 | 875 | 33.38 |
| 10-06 | 1030 | 32.89 |
| 10-07 15:13 | 1155 | 30.19 |

后续约 16:30–16:45 的 MANIFEST 快照为 1171 个文件、737 个小于 1 MiB 的文件。下表按小文件的起始 slot 分组，不与前一快照混用分母。

| 小文件起始 slot | 小于 1 MiB 的文件数 | 占 737 个小文件的比例 |
|---|---:|---:|
| 1088 | 421 | 57.1% |
| 498 | 205 | 27.8% |
| 2432 | 34 | 4.6% |
| 1827 | 26 | 3.5% |
| 其他 | 51 | 6.9% |
| 合计 | 737 | 100% |

slot 498、1088 合计 626 个小文件，占 84.9%。对照 WAL 中两个 slot 仅占 0.056% 的不同 key，现有数据更支持“特定存储边界反复产生碎片”，而非这两个 slot 在采样期有大量写入。存量文件和请求样本不是同一时间跨度，不能用这两个比例计算长期写放大。

**3. 两个集中位置，都有下一 slot 的旧尾文件作为边界**

| 碎片集中的 slot | 下一 slot 的旧尾文件 | 大小 | 尾文件生成时间 |
|---|---|---:|---|
| 498 | #90521，slot 499 | 3,109,364 B ≈ 2.97 MiB | 10-02 00:59:35 |
| 1088 | #73132，slot 1089 | 1,867,276 B ≈ 1.78 MiB | 09-30 19:09:01 |

两个尾文件都由普通 `1@L5 + 5@L6 → L6` 任务生成，输出形态均为五个约 128 MiB 的文件，加一个不足目标大小的尾文件。

尾文件刚生成时，前一个满文件仍跨到同一 slot：#90520 覆盖 slot 488–499，#73131 覆盖 slot 1077–1089。因此，“尾文件刚生成”与“后来新 key 位于 L6 空隙”是不同时间的布局；后续 compaction 改变文件边界，参与了最初碎片的形成。

早期已出现可重建的同类切分：

| 新 L5 小文件 | 所在 slot / 大小 | 下一输出前新计入的 L6 文件 |
|---|---|---|
| #79606，10-01 06:02 | 1088 / 551,420 B | #73132 + #78462（后者约 128 MiB） |
| #95353，10-02 09:50 | 498 / 334,315 B | #90521 + #94998（后者约 128 MiB） |
| #96465，10-02 11:35 | 498 / 227,057 B | #90521 + #96343（后者约 128 MiB） |

这三个小文件都是所属任务的第一个输出，与当时 L6 无重叠。它们表明：最初生成小文件不需要先存在很长的旧碎片串；任务从 slot 尾部开始，再在下一 slot 前提前结束输出，就能留下小文件。

**4. 完整样本：#158375 如何变成只有 1 条记录的 L6 文件**

10 月 6 日 12:14:34，JOB 42980 执行 `1@L4 + 24@L5 → L5`，输入、输出均为 50,529 条记录，共生成 29 个 SST。其中 #158375 位于输出序列中间，只有 3185 B、1 条记录，属于 slot 498；下一文件 #158376 从 slot 499 开始。

重放该任务提交前的 MANIFEST，得到以下 key 范围关系（m、s 是示意名称）：

```text
合并输出的相邻 key：       m：slot 498 新 ID           s：slot 499 新 ID
                         位于 L6 空隙                 位于 B 的范围内
L6 的顺序：旧 slot 498 文件串 → m → [A：slot 499 旧 ID] → [B：slot 499…509]
                                        #90521               #157811
                                        2.97 MiB             128.24 MiB
```

写入 s 前，从 m 推进到 s：进入 A、离开 A、进入 B，跨过 3 个边界；新增计入大小为：

```text
3,109,364 + 134,465,913 = 137,575,277 B ≈ 131.2 MiB
128 MiB / 8 = 16,777,216 B = 16 MiB
131.2 MiB > 16 MiB
```

符合 RocksDB 9.3.1 的 skippable-grandparent 切分条件，且该分支没有当前输出文件的最小大小要求。于是 s 写入前关闭 #158375，再创建 #158376。判断增量包含 A 和 B 的完整大小，但未来能省下的是 A 的读取、重写；B 仍与从 s 开始的输出重叠。

#158375 与当时 L6 无重叠。日志随后直接记录：

```text
2026/10/06-12:14:36.270290 ... Moving #158375 to level-6 3185 bytes
```

当时 LOG 的定位：任务开始在 167122 行、文件创建在 167170 行、移入 L6 在 167212 行。日志轮转后文件名可能变化。

另外两个独立任务也有相同链路：

| 文件 / JOB | 大小 / 记录数 | 跨过边界数 | 新计入 L6 字节数 | 后续日志 |
|---|---|---:|---:|---|
| #138312 / 37904 | 10,831 B / 3 | 3 | 137,489,452 | trivial move 到 L6 |
| #141587 / 38748 | 9,076 B / 3 | 3 | 137,496,504 | trivial move 到 L6 |
| #158375 / 42980 | 3185 B / 1 | 3 | 137,575,277 | trivial move 到 L6 |

三个任务均无记录数减少、只有一个 subcompaction、无压缩。#158375 位于输出中间。这些事实排除了这些样本因大量过期过滤、压缩、并行任务尾部或整个任务最后余量而变小的解释。对应源码见 [compaction_outputs.cc](../rocksdb-9.3.1/db/compaction/compaction_outputs.cc)，尤其 ShouldStopBefore 的 305–329 行。

较早 718 个小文件的来源统计中，688 个出生于 L5，占 95.8%；其中 613 个所属任务的输入、输出记录数相等。这个总体统计支持“小文件主要在上层生成后进入 L6”，但不能替代逐文件的切分分支重建。

**5. 持续积累后，新数据前后都可能被切开**

进入 slot 498 新 ID 之前，已经能完整跳过同 slot 的旧文件串：

| 新小文件生成时刻 | 新数据之前完整跳过的旧文件数 | 合计大小 |
|---|---:|---:|
| #138312，10-05 09:09 | 24 | 19.81 MiB |
| #141587，10-05 13:35 | 43 | 24.04 MiB |
| #158375，10-06 12:14 | 123 | 48.90 MiB |

这些总量均已超过 16 MiB。于是从 slot 497 跳到 slot 498 新数据时可先切一次；从 slot 498 跳到 slot 499 时，又因旧尾文件 A 加大文件 B 切一次。两次切分之间可能只有本轮 slot 498 的 1–3 条记录。

这些新文件进入 L6 后又成为后续可跳过的旧文件，形成持续积累。这个过程不要求某个 SST 原地长大，也不要求 slot 498 请求特别多。

业务 TTL 约 12 小时，物理文件却可能留存更久：#158375 内存储的过期时间为 10 月 7 日 00:13:39.472，检查时已经过期约 16.5 小时，文件仍在 L6，在线 PTTL/TYPE 为 -2/none。trivial move 不重写记录，不能顺便过滤过期数据。当前 OPTIONS 中 RocksDB ttl、periodic_compaction_seconds 为 30 天；常规 leveled compaction 也不因 L6 小文件数量多就自动把它们聚合。

**6. 证据能够支持的结论和边界**

可以直接确认文件数增长、请求样本分布、小文件的创建与移动、文件范围以及选定记录的过期留存。结合对应版本源码，三个具体任务满足同一提前切分分支，早期样本和后续旧文件串又解释了形成与增强过程。因此，这条路径是该实例 L6 碎片积累的主要原因，有实际数据支撑。

没有对所有小文件逐个重建，也没有部署带分支计数的二进制或做修复前后对照实验。部署版本日志的 RocksDB Git sha 为 0，无法排除额外补丁。WAL/MANIFEST 解析未重新计算记录 CRC32C，已有统计通过 LOG、MANIFEST 和目录交叉核对。请求均匀性限于采样窗口。上述限制不影响具体文件生命周期的日志事实，但不宜据此断言每个小文件都来自这一分支，或单靠修改一个条件就已验证能解决全部问题。
