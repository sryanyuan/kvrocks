## 遇到了疑难杂症

我们公司使用kvrocks来替换大内存的redis集群，起到了良好的效果，成本节约很可观，长期使用过程中也比较稳定，带来了良好的收益。但是在这个过程中，也遇到了一些问题，其中大部分都可以通过调整集群分片数量等手段解决，但是下面这个案例，还是算是一个“疑难杂症”的。

一个应用使用的kvrocks集群，其实还是比较适合持久化场景的，它会源源不断的写入string类型数据，并且都有同样的TTL。写入量比较恒定，所以理论上磁盘占用也会是比较稳定的，于是在初期上线的很长一段时间内，没人关注到它到底有没有异常，在业务使用角度来看，也很稳定没什么异常，直到有一天问题突然爆发。

![写延迟](pics/write-slowdown.png)

突然出现了大量的写延迟，我们第一时间先进行了主从切换，然而故障依旧。我们查看了写降速原因，主要是pending compaction bytes slowdown/stop。于是我们尝试增加后台线程数量，发现依旧无法恢复。最终我们在从节点强制compact，然后做主从反转后恢复。

事后我们查看了监控以及rocksdb的日志文件，发现了一些奇怪的现象，如何将这些异常和最终的写降速关联到一起呢？

## 异常现象

### 异常的磁盘占用量

我们之前也介绍了业务的写入特性，理论存储空间会比较稳定。我们在监控观察这个集群的磁盘使用情况，发现除了一开始比较稳定，后续磁盘占用空间不断上涨，完全不符合预期。

![异常磁盘占用](pics/large-disk-usage.png)

### L5/L6大量小文件

我们打开了rocksdb的status dump功能，发现L5/L6磁盘占用特别大，理论上整个集群的磁盘占用应该稳定在100G左右

![rocksdb status dump](pics/small-files.png)

从slowdown日志来看，已经积累了大约150G的compaction堆积，触发了写降速。kvrocks默认开启了dynamic level bytes，所以根据上图进行分析，大概每层的详情大概如下图所示：

![dynamic-level](pics/kvrocks-dynamic-level-capacity.svg)

到这里我们大概已经知道问题应该出在异常的L5/L6空间占用了

### 怪异的文件数量

仔细分析L5/L6的统计指标，我们可以发现居然有几万，几十万的文件数量，正常情况下不应该会出现的，对应的平均文件大小只有大约1M，很不正常。所以我们得先看出这些小文件是怎么产生的。

从rocksdb日志中，我们发现了大量小文件的移动日志

```
[db/db_impl/db_impl_compaction_flush.cc:3819] [metadata] Moving #5296091 to level-6 1092746 bytes
EVENT_LOG_v1 {"job": 1514209, "event": "trivial_move", "destination_level": 6, "files": 1, "total_files_size": 1092746}
```

发生了大量的trivial move。为什么会产生trivial move呢？trivial move是rocksdb在compaction过程中的一个优化手段，当层级 L 的某个 SST 文件与层级 L+1 中所有文件的数据范围完全没有交集时，RocksDB 不需要对该文件进行实际的解压、合并和重写，而是直接将该文件从层级 L 移动到层级 L+1。这样可以避免不必要的文件IO，提高性能。

trivial move按理来说合情合理，那么理论上有固定磁盘占用集群的磁盘占用怎么会不受控制的越来越高呢？

## 问题排查

### L6的Compaction策略

我们大概可以看出来，大量的文件都沉在了最底层L6，kvrocks内置了定时的compaction checker，用来挑选文件是否满足compact条件，但是由于带TTL自动过期的key，过期了后不会影响SST的deleted_keys，即使L6的某个SST文件数据都过期了，仍旧可能不会被清理。所以L6文件越堆积越多，大致的链路是这样的：

* SST文件生成时候，key尚未过期，delete_keys达不到compaction的比例
* 与L6文件没有重叠，通过trivial move直接进入了L6
* key都过期了，但是SST的统计信息不会改变
* 新SST继续生成，通过trivial move直接进入L6，不触发compaction
* 文件不断堆积

L6文件堆积的原因大概找到了，所以接下来我们得寻找为什么会产生那么多的小文件，那么多的trivial move

### 小文件产生的原因

我们通过线上不断复制数据到新集群来分析模拟异常情况，发现这种情况是慢慢产生的。我们首先得明白kvrocks的key的编码规则

![kvrocks-key编码](key-encoding/kvrocks-cluster-key-encoding.svg)

如上图所示，假设我们集群的namespace唯一，那么我们在集群模式下，每层的数据分布，是首先根据key的槽位slot来排序的。

我们在抓取了业务流量分析之后，发现业务使用的key是一个字典序不断递增的key，可以理解为一直在追加数据。但是经过slot槽位编码之后，可以理解为同时向16384个槽位不断的在尾部追加数据。

```text
slot 498：旧 ID …… 较新 ID …… 本轮新 ID
slot 499：旧 ID …… 较新 ID …… 本轮新 ID
slot 500：旧 ID …… 较新 ID …… 本轮新 ID
```

这个数据特性会如何影响kvrocks使用的rocksdb在默认配置下的数据分布呢？我们在多次分析之后，发现在正常的compaction过程中，也会生成部分小文件，比如上层大约有几百M的文件compaction进L6，那么它输出的文件结果可能是128M,128M,128M,2M。这种是符合预期的。但是这种情况不会造成更多的小文件，我们得继续分析。

我们统计了不同日期L6的文件数量和尺寸，如下表：

| 采样日期 | L6 文件数 | L6 大小 / GiB（约） |
|---|---:|---:|
| 09-29 | 292 | 30.47 |
| 09-30 | 344 | 30.79 |
| 10-01 | 401 | 30.32 |
| 10-02 | 461 | 29.35 |
| 10-03 | 528 | 28.57 |
| 10-04 | 625 | 29.12 |
| 10-05 | 875 | 33.38 |
| 10-06 | 1030 | 32.89 |
| 10-07 15:13 | 1155 | 30.19 |

我们可以发现L6占用的磁盘空间上升不明显，但是文件数量在不断的上涨。这里首先出现了一个线索：718 个小文件中，**688 个出生于 L5，占 95.8%**。因此，我们得看看它们是怎么生成的，又是怎么进入L6的。

我们分析了业务的写请求，可以确认槽位分布是均衡的。但是通过MANIFEST的分析，发现了奇怪的现象，L6 的 737 个小文件有 626 个集中在 slot 498、1088，占 **84.9%**。为何小文件大量集中在这两个槽位呢？

![请求槽位分布与 L6 小文件分布对比](l6-small-files-20261007/diagrams/03-request-vs-small-files.svg)

从业务key的特性和kvrocks的编码特性来分析，我们首先可以判定，假设L4需要合并到L5，假设遇到slot的变化，比如从498跳到499，那么大概率498和499中间会有一大片空隙，因为递增的key都是追加在key末尾的。从日志中我们发现了L5产生了绝大部分的小文件，是什么原因呢？

### 接近真相：提前分割

继续查看日志，同时对照rocksdb的文件分割判断，发现了一个很重要的点，就是L4向L5合并的时候，居然会同时参考L6的数据分布来确定数据要不要提前分割！

RocksDB 9.3.1 的 `CompactionOutputs::ShouldStopBefore` 中，这个分支的核心条件如下：

```cpp
const size_t num_skippable_boundaries_crossed =
    being_grandparent_gap_ ? 2 : 3;
if (compaction_->immutable_options()->compaction_style ==
        kCompactionStyleLevel &&
    num_grandparent_boundaries_crossed >=
        num_skippable_boundaries_crossed &&
    grandparent_overlapped_bytes_ - previous_overlapped_bytes >
        compaction_->target_output_file_size() / 8) {
  return true;
}
```

从这个实现中，我们可以看到提前分割的几个条件，以L4合并到L5为例：

* 跨越边界
  * 假设当前key落到L6某个文件中间，则需要跨越三个边界
  * 假设当前key落到L6的文件间隙中，则需要跨越两个边界
* 当前key新覆盖的文件大小

第一个条件主要是为了确保当前key和上一个key之间跨越了至少一个文件，第二个条件是当前key新覆盖的L6文件的尺寸之和。当这两个条件满足之后，当前key不会写入新的SST，提前分割，再以当前key为起点创建新的SST继续上述逻辑。

这个优化点主要是为了防止不必要的IO。假设两个key中间跨越了下层的文件并且满足了对应的文件尺寸，那么提前切割的确是更好的选择，至少覆盖的那些文件下次compaction的时候完全不会选择到，因为完全没有覆盖。

![一次提前切分的边界计算与输出文件变化](l6-small-files-20261007/diagrams/02-l4-l5-early-split.svg)

我们以日志实际记录的compaction job为例，看看这个案例下是怎么触发小文件生成的

JOB 42980 执行 `1@L4 + 24@L5 → L5`。输入、输出均为 50,529 条记录，生成 29 个 SST。

其中 #158375 处于输出序列中间，只有 **3185 B、1 条记录**，key 属于 slot 498。下一个输出文件 #158376 从 slot 499 开始。

我们分析当时的MANIFEST，可以获得以下信息

| 角色 | 文件或 key | 范围 / 大小 |
|---|---|---|
| 已写入的 m | #158375 的唯一 key | slot 498；与当时 L6 无重叠 |
| 完整跳过的 A | #90521 | slot 499 旧 ID；3,109,364 B |
| 新进入的 B | #157811 | slot 499–509；134,465,913 B |
| 待写入的 s | #158376 的首 key | slot 499；落在 B 的范围内 |

从 m 推进到 s，进入 A、离开 A、进入 B，恰好三个边界。新增计入大小为：

```text
3,109,364 + 134,465,913 = 137,575,277 B
                           ≈ 131.2 MiB > 16 MiB
```

它满足之前说的提前分割条件。由于 m 本身与 L6 无重叠，生成的小 SST 随后可以通过 trivial move 直接进入 L6。我们也可以看到对应的日志:

```text
2026/10/06-12:14:36.270290 ... Moving #158375 to level-6 3185 bytes
```

### 最初小文件是怎么产生的

我们上面已经分析出L5小文件为何频繁产生，但是最初正常写入情况下，为什么会产生小文件从而触发越来越多的小文件呢？

slot 498 和 slot 1088 后面，分别有一个长期保留的旧尾文件：

| 碎片集中的 slot | 下一 slot 的尾文件 | 生成时间 | 大小 |
|---|---|---|---:|
| 498 | slot 499 的 #90521 | 10-02 00:59:35 | 2.97 MiB |
| 1088 | slot 1089 的 #73132 | 09-30 19:09:01 | 1.78 MiB |

两者都来自正常的  `1@L5 + 5@L6 → L6` 合并：依次生成五个约 128 MiB 的文件，输入结束时再留下一个残留的文件。这种残留的小文件本身是正常现象。

刚生成 #90521 时，前一个满文件 #90520 覆盖 slot 488–499。后续 compaction 又改变了周围文件的边界，才逐渐出现“slot 498 新 ID 在空隙中，后面紧接 slot 499 旧尾文件和大文件”的布局。不能把这两个时刻当成同一张快照。

早期样本 #95353 只有约 326 KiB，位于 slot 498，是所属任务的第一个输出文件。下一输出从 slot 499 开始，中间跨过 #90521，再进入约 128 MiB 的 #94998。这个早期小文件与当时 L6 无重叠，已经具备直接移入 L6 的条件。

slot 1088 也存在对应样本：#79606 大小 551,420 B，是任务第一个输出，后面跨过 #73132，再进入大文件 #78462。

这说明最初的小文件不依赖“前面已经有很多碎片”。任务恰好从某个 slot 的尾部开始，随后在下一 slot 前提前结束输出，就足以形成一个小文件。

![从正常尾文件到持续积累的 L6 碎片](l6-small-files-20261007/diagrams/01-l6-fragmentation-timeline.svg)

图 4：各阶段对应不同时间。少量历史尾文件提供了边界，后续切分和移动才逐步积累出大量碎片。

运行更久后，另一侧的切分条件也逐渐满足。进入 slot 498 的新 ID 之前，已经可以完整跳过一串同 slot 的旧文件：

| 新小文件生成时刻 | 前面完整跳过的旧文件数 | 总大小 |
|---|---:|---:|
| #138312，10-05 09:09 | 24 | 19.81 MiB |
| #141587，10-05 13:35 | 43 | 24.04 MiB |
| #158375，10-06 12:14 | 123 | 48.90 MiB |

这些总量均超过 16 MiB。于是，新数据进入 slot 498 前可以先切一次，离开 slot 498 时又因 slot 499 的尾文件和大文件再切一次。两次切分之间，只剩本轮 slot 498 的少量新 key。

新小文件进入 L6 后，又成为下一轮可跳过的旧文件之一。逐渐增长的是旧文件串的数量和累计大小，SST 本身不会原地长大。
